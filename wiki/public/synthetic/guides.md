# Practical build guides

All guides are fictional workshop examples, not scheduled services, adopted methods, staff support, or guaranteed outcomes. Every record is sample-only. Introduce answers with “In this fictional demo…”. See [store rules](index.md).

## GUIDE-001 — Start in thirty minutes

Example: spend five minutes naming one person and one small problem, five sketching a possible screen, fifteen making a paper or HTML prototype, and five trying one task. Deliverable: one testable interaction and one unanswered question. Cut login, payments, databases, and integrations from this first version. Try [PROJECT-002](projects.md); the timing is a hypothetical exercise, not an event schedule.

## GUIDE-002 — Choose a tiny scope

Example: rewrite “build a community platform” as “help a visitor compare three sample activity cards”. Write one must-have, two optional additions, and a clear stop condition. Build the must-have first. Deliverable: a one-paragraph scope card. If it cannot be shown in two minutes, remove a feature rather than adding teammates. See [SUPPORT-001](support.md).

## GUIDE-003 — Find a useful role without coding

Example roles: interviewer drafts three neutral questions; writer improves labels; designer sketches the flow; tester notes confusing steps; storyteller prepares the demo. In a fictional pair, switch roles after one test so both people learn. Deliverable: a sketch plus one concrete improvement. These are roles someone could try, not real member profiles or a matching service.

## GUIDE-004 — Test with three people

Example: show a prototype, give one realistic task, stay quiet, and record where each volunteer hesitates. Ask “What did you expect?” rather than “Do you like it?”. Summarise observations without names or private details. Deliverable: three observations and one change to try next. Participation must be voluntary; do not claim three actual testers are available.

## GUIDE-005 — Plan a two-hour build

Example allocation: 15 minutes choose a problem, 20 sketch, 45 build one interaction, 20 test, 10 improve, 10 share. Assign a navigator and maker, then swap. Deliverable: a rough prototype with a README describing assumptions and next steps. This is a reusable fictional exercise, not a confirmed session time or host commitment.

## GUIDE-006 — Share unfinished work

Example two-minute demo: explain the intended user, show one action, name one surprise, and ask one feedback question. A failed experiment can be a useful result if its lesson is clear. Deliverable: a screenshot or paper sketch with a short explanation. Obtain permission before showing anyone's face, name, or contribution; no real permission is implied.

## GUIDE-007 — Make a beginner-friendly handover

Example README sections: what the prototype does, how to open it, which data is fictional, one known limitation, and the smallest next task. Use plain language and a screenshot without personal data. Deliverable: instructions another person can follow without the original maker. Never put keys or secrets in a public repository.

## GUIDE-008 — Check accessibility early

Example prototype checks: descriptive labels, keyboard navigation, visible focus, readable contrast, and status messages that do not depend on colour alone. Try a narrow phone viewport and larger text. Deliverable: a short issue list, not certification or proof of legal compliance. This guide does not establish that any Oslo venue is accessible. See [PROJECT-011](projects.md).
