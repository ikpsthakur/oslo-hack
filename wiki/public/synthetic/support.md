# Collaboration support playbook

These are fictional self-help examples, not a staffed support desk, organiser response promise, or adopted policy. Every record is sample-only. Label answers as a fictional demo. No actual participant or contact details are stored. See [store rules](index.md).

## SUPPORT-001 — Too many ideas

Example: each person writes a problem in one sentence. Compare usefulness, ability to test today, and comfort with the tools. Choose the smallest reversible experiment, not the most ambitious product. Put the other ideas in a “later” list. Next action: use [GUIDE-002](guides.md) to define one must-have.

## SUPPORT-002 — Nobody knows how to code

Example: make a paper interface, clickable slides using existing tools, or a set of printed cards. Test whether a person understands the flow before building software. Next action: sketch [PROJECT-004](projects.md). No equipment loan, training class, or available mentor is promised.

## SUPPORT-003 — The API or internet is unavailable

Example: replace the dependency with five clearly labelled mock records and demonstrate the intended flow. Keep the failure visible in the README; never describe mock results as live data. Next action: prototype [PROJECT-001](projects.md) offline. Reconnect a real API only after checking its access and terms.

## SUPPORT-004 — A teammate feels left out

Example: pause, ask what each person wants to try, split off one small task, and rotate maker/navigator roles. Explain unfamiliar words without testing someone's competence. Next action: pick a non-code role from [GUIDE-003](guides.md). This is a collaboration example, not evidence that a mediator is present.

## SUPPORT-005 — We disagree on a design

Example: draw both options and give each the same small test. Compare what people can complete rather than whose idea wins. If evidence is unclear, choose the simpler reversible option and note the uncertainty. Deliverable: one decision and a reason, not a promise of consensus.

## SUPPORT-006 — We are running out of time

Example: freeze new features, keep one working path, label unfinished parts, and spend the last ten minutes preparing a demo. A paper explanation can stand in for an unbuilt screen only if called a mock-up. Next action: use [GUIDE-006](guides.md). No real workshop deadline is implied.

## SUPPORT-007 — Can the chatbot connect me with a person?

Boundary: this assistant is not live human support, a member directory, a recruiting service, or an organiser inbox. It cannot send messages or arrange a meeting. It can suggest a fictional team-role combination and questions to ask a future organiser. Actual contact details remain unconfirmed in the baseline guide.

## SUPPORT-008 — My question needs real facts

Boundary: actual dates, venue, accessibility, fees, places, booking, policies, and organiser contacts require verified information. Fictional examples cannot fill those gaps. Explain the unknown plainly and offer a labelled planning example only if useful. The assistant has no live web lookup or ticket system; never say an issue was submitted.
